CMS blocks: a page builder

Editorial sites (WEF's included) aren't hand-written pages. Editors compose pages in a CMS from blocks (hero, text, stats, chart, quote, call to action) and the frontend maps each block type to a component. Same idea as a Sanity page builder with <PortableText components={…}> in Next.js.

How it works

  1. A content model (cms/blocks.ts): one TypeScript type per block, joined in a union on _type. In a Sanity project, sanity typegen generates exactly this from the schema.
  2. One component per block (cms/*-block.ts): each takes a single typed block input and knows nothing about the CMS, pages or other blocks. That's the design-system part: small, composable, reusable.
  3. A renderer (cms/block-renderer.ts): @for over the blocks, track block._key, and a @switch (block._type) that picks the component. Inside each @case, Angular narrows the type, so passing a StatsBlock to the hero component is a compile error.
  4. A route that loads a document: ?page= → httpResource → renderer. Title and meta description come from the document, on the server too.

Details that matter in production

  • Unknown blocks: the Davos document contains a video block this frontend has no component for (the CMS schema often moves faster than the code). @default shows a warning in development and renders nothing in production, instead of crashing the page.
  • Heavy blocks are deferred individually: the chart sits in @defer (on viewport) inside its @case, so a page without charts never downloads chart code, and a page with one loads it on scroll. A 3D or data-viz block would do the same.
  • Rich text without innerHTML: text arrives as structured spans (≈ Portable Text) and becomes real <strong>, <em> and link elements. Nothing from the CMS is parsed as HTML, so there's nothing to sanitise and no injection risk. (If you must render CMS HTML, Angular's [innerHTML] sanitises it, but structured content is better.)
  • Links: internal CMS links become routerLinks (no full reload); external ones stay plain links.
  • Only the first hero gets priority: it's the LCP image (lesson 11). $first from the loop decides.
  • Editor tooling: "show block outlines" labels each block with its type, a tiny version of Sanity's Presentation tool / visual editing overlay.

The alternative: a component registry

Instead of @switch, some codebases keep a map from type to component and render it dynamically:

const BLOCKS: Record<string, Type<unknown>> = { hero: HeroBlockComponent, stats: StatsBlockComponent, … };

Beyond this demo

  • Real CMS: replace the JSON files with the Sanity client / a GROQ query in a service. The renderer doesn't change.
  • Caching & revalidation: the Express server (src/server.ts) is where a CMS webhook endpoint would clear a cache or re-prerender a page when an editor publishes, like your casedeschise.ro setup.
  • Preview / drafts: a route that loads draft documents with a token, rendered with RenderMode.Server so editors see changes immediately.
  • Animation: blocks can opt into motion with the lesson 14–16 helpers (useGsap, enter/leave hooks), so a "scroll story" is just another block type.
