Lesson 12

SSR & hydration

Until now this site was a client-side app: the server sent an empty <app-root> and the browser built everything. Now it's server-rendered. The HTML arrives complete (good for SEO, link previews and first paint), and Angular then hydrates it: it attaches to the existing DOM instead of rebuilding it. After that, navigation is client-side again, exactly like Next.js.

1. The same component, run twice

  • "rendered on" says server in the page source and browser on screen: the browser re-ran the constructor and updated that text during hydration.
  • The server time comes through TransferState: the server writes it into the HTML as JSON, and the browser reads it instead of computing its own. That's how you avoid values that change between server and browser (dates, random IDs).

2. HTTP transfer cache: fetch once, on the server

This page loads /api/talks.json. During SSR the server fetches it and embeds the response in the HTML. When the browser hydrates and makes the same request, it's answered from that cache. No network call.

Loaded {{ talks().length }} talks. Real network requests for /api/talks.json since this tab loaded: {{ networkRequests() ?? '…' }}
  • After a reload: 0, answered from the transfer cache. Navigate to another lesson and back: the browser fetches it itself and the count goes up. In Next.js terms: the server's fetch result is passed down instead of fetched again.
  • The count comes from the browser's Performance API, not from our lesson 07 interceptor, because your interceptors run before Angular's built-in ones (the transfer cache, and the one that resolves relative URLs like /api/… on the server). An interceptor in front of the cache sees cached responses too.
  • That ordering also means: never turn URLs absolute in your own interceptor for SSR. The cache key would differ between server and browser, and every request would be made twice. (I hit exactly that while building this lesson.)

3. Incremental hydration: HTML now, JavaScript later

Every probe below is fully server-rendered (you can read it immediately). The difference is when its JavaScript wakes up. Reload the page to see it; after client-side navigation, all blocks are created normally.

@defer (on immediate; hydrate on interaction) { } @defer (on immediate; hydrate never) { }
  • on interaction: stays inert until you click it. Thanks to event replay, that first click isn't lost: it triggers hydration and is then replayed, so the counter goes to 1.
  • never: stays server HTML forever. Clicking does nothing. Perfect for static content like an article body or a footer.
  • This is how a long editorial page can ship a 3D hero or a chart without paying for its JavaScript up front, while still showing real content (not a placeholder) to readers and search engines.
  • hydrate … triggers only apply to the first, server-rendered load. After in-app navigation there is nothing to hydrate, so the regular trigger in the same block decides (on immediate, on viewport). Without one, the block wouldn't render at all after navigating here (another thing I hit while building this).

4. What runs where: the rules

  • On the server: constructors, field initializers, computed, effect, ngOnInit, templates, HTTP calls, guards and resolvers.
  • Browser only: afterNextRender / afterEveryRender. That's where DOM libraries (GSAP, Three.js), window, localStorage, matchMedia, timers and observers belong.
  • When you need to branch: isPlatformBrowser(inject(PLATFORM_ID)) (≈ typeof window !== 'undefined' in Next.js).
  • Never-ending timers started on the server keep the app from becoming "stable", so the server render never finishes.

Also good to know

  • Hydration mismatches happen when the browser's first render differs structurally from the server HTML: browser-only branches in templates, third-party scripts editing the DOM early (A/B testing tools, consent banners). Angular logs them in dev mode. ngSkipHydration on a component opts it out (≈ dynamic(..., { ssr: false })).
  • Angular has no React Server Components: every component's JS is still sent to the browser. Incremental hydration and @defer are how you delay paying for it.
  • ng serve now renders on the server too. npm run build + npm run serve:ssr:learn-angular runs the real Express server from src/server.ts on port 4000.
