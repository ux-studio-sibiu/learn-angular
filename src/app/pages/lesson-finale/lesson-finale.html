The decisions behind it

  • GSAP tweens a plain object, not the 3D objects and not signals. params is the single source of truth for the scene. GSAP can interpolate any number (and colour strings) on any object, and one render() applies them. That keeps GSAP unaware of three.js, and three.js unaware of scroll.
  • One loop. Three.js renders from gsap.ticker instead of its own setAnimationLoop, so scroll smoothing and rendering happen in the same frame (loop strategy C). It's added outside the zone and only while the canvas is on screen.
  • Only meaningful changes reach Angular (loop strategy B): the chapter index, through a signal, into an OnPush component.
  • Content first. The captions are real HTML rendered by Angular, on the server too. Without WebGL, without JS, with reduced motion, the story is still there to read. The 3D is enhancement.
  • Reduced motion (lesson 05's switch): no pin, no scrub, one still frame, chapters as a list. useGsap rebuilds the setup when it changes.
  • Lazy and server-safe: the server renders the poster; GSAP and three.js arrive only when the block scrolls into view (@defer); nothing touches window before afterNextRender.
  • Clean exit: navigate away and the context reverts (timeline, ScrollTrigger, pin spacer), the ticker callback is removed, and every geometry, material and the WebGL context are disposed.

The 30-second version

"Angular owns structure, content and state; GSAP owns time and scroll; Three.js owns pixels. They meet at three narrow points: GSAP tweens a plain parameters object that the render function reads, both run on one ticker outside Angular's zone, and only meaningful changes, like the active chapter, become signals in OnPush components. The content is server-rendered HTML, the 3D is deferred until it's on screen, reduced motion gets a static version from one shared preference, and everything is reverted and disposed when the component is destroyed."
